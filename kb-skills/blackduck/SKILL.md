# Black Duck 점검 결과 조회

`config.properties`에 설정된 Black Duck 서버에서 이미 스캔된 결과를 조회합니다. 명령은 저장소 루트에서 실행합니다.

```sh
python3 .claude/skills/blackduck/scripts/blackduck.py <명령> [--project 프로젝트] [--version 버전]
```

Python 3.9 이상이 필요하고, 표준 라이브러리만 사용합니다. Windows에서 `python3`가 없으면 `python`이나 `py -3`으로 실행합니다.

## 이 스킬이 하지 않는 일

- **스캔을 실행하지 않습니다.** Detect를 설치하거나 실행하지 않습니다. "점검해줘", "블랙덕 돌려줘" 같은 요청에는 스캔은 이 스킬에서 할 수 없다고 밝히고, 서버의 최신 결과를 조회해 답합니다. 결과가 오래됐다면 팀의 스캔 절차로 다시 스캔한 뒤 조회하라고 안내합니다.
- **변경하지 않습니다.** 스크립트는 토큰 인증을 제외하면 GET만 호출하므로 조치 상태, 정책, BOM을 바꿀 수 없습니다. 토큰 계정에 쓰기 권한이 있어도 마찬가지입니다. 사용자가 명시적으로 요청하지 않으면 의존성이나 코드도 수정하지 않습니다.

## 조치 기준

모든 답변은 이 기준으로 판정합니다.

### 판정

| 판정 | 조건 | 답변에서 표현 |
|---|---|---|
| `BLOCK` | 차단 항목이 1건 이상 | 필수 조치 |
| `REVIEW REQUIRED` | 차단 항목은 없고 검토 항목이 1건 이상 | 검토 필요 |
| `PASS` | 차단 항목과 검토 항목이 없음 | 조치 없음 |

### 라이선스 기준

컴포넌트의 라이선스를 SPDX ID로 분류합니다. `api`로 조회한 BOM의 `spdxId`를 쓰고, 값이 없으면 라이선스 이름과 패밀리로 판단합니다. `A OR B`는 허용되는 쪽을 선택할 수 있으므로 가장 낮은 위험으로, `A AND B`는 가장 높은 위험으로 분류합니다.

| 분류 | 라이선스 | 조치 |
|---|---|---|
| 허용 | MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, 0BSD, Unlicense, CC0-1.0 | 사전 승인 없이 사용 |
| 검토 | LGPL-2.0, LGPL-2.1, LGPL-3.0, EPL-1.0, EPL-2.0, MPL-2.0, CDDL-1.0, CDDL-1.1, 벤더 승인을 받은 상용 SDK | 링크 범위, 수정 여부, 배포 형태 검토 |
| 차단 | GPL-2.0, GPL-3.0, AGPL-3.0, SSPL-1.0, 미승인 상용 라이브러리, 라이선스 불명(`Unknown License`) | 예외 승인 없이 사용 불가 |

- **버전 표기:** `-only`, `-or-later` 여부와 관계없이 같은 라이선스로 봅니다. 서버는 AGPL을 `AGPL-3.0`으로 표기합니다.
- **목록에 없는 라이선스:** 허용으로 간주하지 않고 검토 항목으로 분류해 "정책 미등재"라고 적습니다. PSF-2.0, Zlib, BSL-1.0, CC-BY-4.0, CNRI-Python 등이 해당합니다.
- **테스트 전용 예외:** 약한 카피레프트가 `test`, `testImplementation`, `devDependencies` 범위에서만 쓰이면 허용합니다. BOM만으로는 범위를 알 수 없으므로 의존성 파일로 확인한 경우에만 적용합니다.

### 보안 기준

| 조건 | 분류 |
|---|---|
| CRITICAL 취약점 | 차단 |
| 알려진 exploit이 있는 취약점 (CVSS 무관) | 차단 |
| HIGH 취약점 | 검토 |
| 24개월 이상 릴리스가 없는 컴포넌트 | 검토 |
| MEDIUM, LOW 취약점 | 판정에 넣지 않고 건수만 추적 |

- **exploit 확인:** `vuln <BDSA ID>`의 `exploitPublishDate`가 있으면 차단으로 분류합니다. 이 값은 exploit 공개 정보이며 실제 악용 여부를 뜻하지는 않으므로 근거를 함께 적습니다. 값이 없어도 exploit이 없다고 단정하지 않습니다.
- **조치 상태:** `IGNORED`는 예외 승인이 아니므로 차단과 검토 판정에 포함합니다. 그 밖에 닫힌 상태(`PATCHED` 등)는 판정에서 빼고 건수를 적습니다.
- **릴리스 시점:** BOM의 `releasedOn`은 스캔 시각으로 나오는 경우가 있어 쓰지 않습니다. `activityData.lastCommitDate`는 참고만 하고, 릴리스 이력을 확인하지 못했으면 그렇게 적습니다.

### 예외와 최종 승인

- **예외 승인:** OSS Manager의 서면 승인이 확인된 항목만 승인으로 인정합니다. 승인은 패키지와 항목(라이선스 또는 CVE) 하나에 적용되고, 유효기간이 지나면 인정하지 않습니다. 버전이 바뀌어 라이선스가 달라지거나 새 CVE가 생기면 새 승인이 필요합니다. 승인 여부를 확인할 수 없으면 승인되지 않은 것으로 판정합니다.
- **최종 판단:** 이 스킬의 판정은 권고입니다. 카피레프트 사용, 상용 SDK, HIGH 취약점 면제의 최종 승인은 OSS Manager가 합니다. SaaS라는 이유로 검토 항목을 승인된 것으로 처리하지 않습니다.
- **배포 형태 변경:** 모바일이나 데스크톱 바이너리를 배포하는 프로젝트이면 약한 카피레프트(LGPL, EPL, MPL, CDDL)를 검토가 아니라 차단으로 분류합니다. AGPL, SSPL은 SaaS에서도 소스 공개 의무가 생길 수 있어 차단입니다.
- **범위 밖:** 정책의 금지 코드 패턴(하드코딩된 자격 증명 등)은 Black Duck으로 판정하지 않습니다.

## 서버 정책 상태 해석

서버 정책 상태는 참고 정보로 함께 적습니다. `status`의 `Policy` 값을 그대로 씁니다.

| Policy 값 | 의미 |
|---|---|
| `IN_VIOLATION` | 정책 위반 있음. `violations`로 컴포넌트와 규칙을 확인합니다. |
| `NOT_IN_VIOLATION` | 정책 위반 없음. 취약점이 0건이라는 뜻은 아닙니다. |
| 그 외 값 | 값을 그대로 전하고 위반 없음으로 단정하지 않습니다. |

- 규칙의 severity `UNSPECIFIED`는 "낮음"이 아니라 등급이 지정되지 않았다는 뜻입니다. 규칙 이름과 설명으로 판단합니다.
- 정책을 위반하지 않은 CRITICAL 취약점도 숨기지 않습니다. 위반 항목과 구분해 적습니다.

## 설정

서버 URL, API 토큰, 기본 프로젝트와 버전은 `.claude/skills/blackduck/config.properties`에 있습니다. 스크립트가 실행할 때마다 이 파일을 읽으므로 수정하면 바로 적용됩니다.

```properties
url=<Black Duck 서버 주소>
token=<API 토큰>
project=<프로젝트 이름>
version=<버전 이름>
```

이 설정은 `blackduck-notice` 스킬도 함께 씁니다. 처음 사용한다면 `config.example.properties`를 `config.properties`로 복사한 뒤 값을 채웁니다. 토큰은 Black Duck 사용자 메뉴의 My Access Tokens에서 발급합니다. `config.properties`는 git에 올라가지 않습니다.

사용자가 값 변경을 요청하면 해당 줄을 수정합니다. 토큰은 출력하거나 명령줄에 넣거나 답변에 포함하지 않습니다.

프로젝트나 버전을 지정하지 않았고 후보가 여러 개이면 스크립트가 오류와 함께 후보 목록을 출력합니다. 임의로 고르지 말고, 질문에서 대상을 알 수 없으면 `projects`, `versions` 결과를 보여주고 사용자에게 묻습니다.

## 명령

| 질문 | 명령 |
|---|---|
| 어떤 프로젝트와 버전이 있는가? | `projects [-q 이름]` |
| 버전별 정책과 스캔 상태는? | `versions --project <프로젝트>` |
| 전반적인 상태는? | `status` |
| 정책을 위반한 컴포넌트와 규칙은? | `violations [--rule 규칙명 일부]` |
| 어떤 정책 규칙이 걸렸는가? | `policies` |
| 미조치 취약점은? | `vulns [--severities CRITICAL,HIGH] [--component 이름] [--limit 50]` |
| 닫힌 항목까지 포함하면? | `vulns --all` 또는 `vulns --statuses IGNORED` |
| 이 CVE/BDSA는 무엇이고 영향이 있는가? | `vuln CVE-2021-44228 --project <프로젝트> --version <버전>`. 프로젝트가 지정되지 않으면 영향 범위는 확인하지 않습니다. |
| 어떤 컴포넌트가 있는가? | `components [-q 이름] [--security CRITICAL,HIGH] [--license-risk HIGH] [--policy IN_VIOLATION]` |
| 어느 버전으로 올려야 하는가? | `upgrade <이름 또는 origin id 일부>` |
| 그 외 읽기 전용 호출 | `api <경로> key=value`. HTTP 406이면 `--accept <미디어 타입>`을 지정합니다. |

명령은 `--project`, `--version`을 받습니다. `projects`는 받지 않고 `versions`는 `--project`만 받습니다. `vulns`, `components`, `violations`, `upgrade`는 `--limit`건만 나열하지만 전체 건수와 집계는 조건에 맞는 전체를 기준으로 합니다. 일부만 보여줄 때는 그 사실을 밝힙니다.

## 결과 해석

- **건수의 단위를 구분합니다.** 서로 더하거나 비교하지 않습니다.
  - `vulns`의 finding은 컴포넌트 origin과 취약점의 조합입니다. 같은 취약점이 여러 origin에서 반복되므로 finding 수와 unique 수를 함께 적습니다.
  - CVE와 BDSA가 같은 취약점을 가리킬 수 있습니다(`related=`). unique 수에는 둘 다 따로 잡히므로 "서로 다른 결함 수"라고 표현하지 않습니다.
  - `status`의 Risk 표는 컴포넌트마다 가장 높은 위험 하나로 센 값입니다. 취약점 건수가 아닙니다.
  - `status`, `policies`의 서버 요약(`Server summary`, `server_violation_count`)은 BOM 행과 단위가 다릅니다. **위반 컴포넌트 수는 `violations`의 수치로 보고합니다.**
- **기본 `vulns`는 조치 상태가 닫힌 항목을 뺍니다.** 닫힌 상태는 `IGNORED`, `PATCHED`, `MITIGATED`, `REMEDIATION_COMPLETE`, `DUPLICATE`, `NOT_AFFECTED`입니다. `IGNORED`는 해결이 아니라 제외입니다. 제외 건수를 답변에 적고, CRITICAL이 포함되면 그 사실도 적습니다.
- **exploit 정보는 `vulns`에 없습니다.** `vuln <BDSA ID>`의 `exploitPublishDate`로 확인합니다. CVE 레코드에는 이 값이 없을 수 있으므로 `related:`의 BDSA도 조회합니다. 값이 없다고 exploit이 없다고 단정하지 않습니다.
- **결과는 마지막 스캔 시점 기준입니다.** `last_scan`이 최근 커밋보다 이전이면 현재 코드가 반영되지 않았다고 밝힙니다. 수정한 항목도 재스캔 전에는 그대로 남습니다.
- **스캔 대상을 추정하지 않습니다.** 서버에는 git 리비전이 없습니다. `status`의 Code locations 이름과 프로젝트 이름으로 이 저장소를 스캔한 결과인지 확인하고, 알 수 없으면 그렇게 말합니다.
- **컴포넌트는 의존성 매칭과 파일 시그니처 매칭으로 잡힙니다.** `match=`가 `FILE_DEPENDENCY_TRANSITIVE`이면 전이 의존성, `FILE_DEPENDENCY_DIRECT`이면 직접 의존성입니다. 시그니처 매칭(`FILE_EXACT` 등)은 오탐이나 다른 버전일 수 있어 실제 사용 여부를 확인합니다.

## 조치 가이드

KB 기준의 조치 대상, 정책 위반, CRITICAL 취약점의 해결 방법을 물으면 건수만 알리고 끝내지 않습니다. 먼저 다음을 확인합니다.

1. `violations`로 위반한 규칙을 확인합니다.
2. `vuln <ID>`로 내용, solution, workaround를 확인합니다. BDSA에 더 자세한 내용이 있는 경우가 많습니다.
3. `upgrade <이름>`으로 권장 버전과 매칭 파일을 확인합니다.
4. 대상 저장소의 의존성 파일(`pom.xml`, `build.gradle`, `requirements.txt`, `package.json` 등)과 호출 코드를 직접 읽습니다.

항목마다 다음 내용을 적습니다.

- **컴포넌트와 위반 사유:** 컴포넌트, 버전, origin, 위반 규칙, 대표 취약점.
- **영향 확인:** 취약한 기능을 실제로 쓰는지와 그 근거. 코드를 확인하지 못했으면 그렇게 적습니다.
- **조치 방법:** 권장 버전과 수정 위치. 전이 의존성이면 어떤 직접 의존성을 올리거나 고정해야 하는지 적습니다. 메이저 버전 변경이면 호환성 위험을 적습니다.
- **검증 방법:** 실행할 테스트와, 재스캔 후 `violations`로 해당 항목이 사라졌는지 확인하는 절차.

`upgrade`의 `short`, `long`은 서버가 제시한 후보이고 `remaining`은 그 버전에 남은 취약점 수입니다. 호환성은 보장하지 않습니다. `guidance`와 `transitive`의 값이 다르면 둘 다 전합니다. "No Solution Available" 류의 규칙을 위반한 컴포넌트에 업그레이드 후보가 나올 수 있는데, 이때는 어느 한쪽으로 단정하지 말고 `vuln`의 solution을 함께 보여줍니다. 의존성 매칭은 `matched files listed`가 0일 수 있으며, 위치는 의존성 파일에서 찾습니다.

가이드는 안내만 합니다. 사용자가 요청하기 전에는 의존성이나 코드를 고치지 않습니다.

## 답변

사용자의 언어로 작성합니다. 특정 수치나 CVE를 묻는 질문에는 질문에 답하는 내용만 적습니다.

프로젝트 상태, 문제점, 해결할 항목, 점검 결과를 묻는 질문에는 다음 순서로 답합니다.

1. **판정:** 프로젝트와 버전, KB 기준의 판정. 이어서 서버 정책 상태, 위반 컴포넌트 수와 위반 규칙을 참고 정보로 적습니다.
2. **조치 대상:** KB 기준의 조치 대상을 먼저, 그다음 정책 위반 항목을 위험 높은 순으로 "조치 가이드"의 내용. 많으면 같은 규칙이나 컴포넌트끼리 묶고, 일부만 적었다면 밝힙니다.
3. **범위:** 마지막 스캔 일시, Code locations, 이 저장소의 결과인지 여부, BOM 링크.
4. **취약점:** 미조치 finding 수와 unique 수, 심각도별 건수, 조치 상태로 제외한 건수.
5. **그 외 위험:** 라이선스 위험과 운영 위험을 간단히. 코드를 읽어 확인한 항목과 확인하지 않은 항목을 구분합니다.

스크립트가 HTTP 401 오류를 내면 토큰이 유효하지 않은 것입니다. 새로 발급해 `config.properties`의 `token` 줄에 저장합니다. 서버에 연결할 수 없다는 오류가 나면 `url` 값과 네트워크를 확인합니다. 프로젝트나 버전이 보이지 않으면 토큰 계정의 권한을 확인합니다.
