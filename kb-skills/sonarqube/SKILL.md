# SonarQube 점검 결과 조회

`config.properties`에 설정된 SonarQube 서버에서 이미 분석된 결과를 조회합니다. 명령은 저장소 루트에서 실행합니다.

```sh
python3 .claude/skills/sonarqube/scripts/sonar.py <명령> [--project 프로젝트키]
```

Python 3.9 이상이 필요하고, 표준 라이브러리만 사용합니다.

## 이 스킬이 하지 않는 일

- **스캔을 실행하지 않습니다.** `sonar-scanner`를 설치하거나 실행하지 않습니다. 분석은 CI 등 각 팀의 분석 절차에서 수행합니다.
- **"점검해줘", "소나 돌려줘" 같은 요청:** 스캔은 이 스킬에서 할 수 없다고 밝히고, 서버의 최신 결과를 조회해 답합니다. 결과가 오래됐다면 팀의 분석 절차로 다시 분석한 뒤 조회하라고 안내합니다.
- **변경하지 않습니다.** 사용자가 명시적으로 요청하지 않으면 코드를 수정하지 않습니다. 이 스크립트는 읽기 전용이므로 이슈, 핫스팟, 게이트, 설정은 변경할 수 없습니다.

## 조치 기준

모든 답변은 이 기준으로 판정합니다.

| 심각도 | 조치 | 답변에서 표현 |
|---|---|---|
| BLOCKER | **반드시 해결** | 필수 조치 |
| CRITICAL, MAJOR, MINOR, INFO | 수정하면 좋지만 하지 않아도 됨 | 권장 사항 |

- **판정 기준:** 해결되지 않은 BLOCKER가 0건이면 필수 조치가 없고, 1건 이상이면 남아 있습니다. `issues --severities BLOCKER`로 확인합니다. 품질 게이트 상태나 등급으로 판정하지 않습니다.
- **BLOCKER가 아닌 항목:** 필수처럼 표현하거나 수정을 재촉하지 않습니다. 심각도가 CRITICAL이어도 권장 사항입니다.
- **오탐으로 보이는 BLOCKER:** 해결된 것으로 치지 않습니다. 필수 조치로 보고하고 오탐으로 판단한 근거를 함께 적습니다.
- **실제 위험을 발견한 경우:** 코드를 읽어 실제 보안 위험이나 장애 위험을 확인했다면 BLOCKER가 아니어도 위험을 분명히 알립니다. 다만 기준상 필수 조치라고 표현하지는 않습니다.

## BLOCKER 수정 가이드

미해결 BLOCKER가 있으면 답변에 항목별 수정 가이드를 포함합니다. 건수만 알리고 끝내지 않습니다. 가이드를 작성하기 전에 다음을 확인합니다.

1. `rule <규칙 키>`로 규칙의 의도와 예시를 확인합니다.
2. `api issues/search issues=<이슈 키>`로 `flows`를 확인합니다. 관련 위치가 여러 줄에 걸쳐 있을 수 있습니다.
3. 플래그된 코드와 `flows`의 위치, 호출하는 코드, 관련 테스트를 직접 읽습니다. 로컬 코드가 분석된 리비전과 다르면 그 사실을 밝힙니다.

항목마다 다음 내용을 적습니다.

- **위치와 문제:** `경로:줄`과 규칙 키, 이 코드에서 왜 지적됐는지.
- **코드 확인 결과:** 실제 결함인지, 오탐으로 보이는지와 그 근거.
- **수정 방법:** 규칙의 일반 예시를 옮기지 말고, 실제 코드를 바탕으로 수정 전후 코드를 보여줍니다. 동작이 바뀌는지도 적습니다.
- **영향 범위:** 함께 고쳐야 할 호출부와 테스트.
- **검증 방법:** 실행할 테스트와, 수정을 커밋해 팀의 분석 절차로 다시 분석한 뒤 `issues --severities BLOCKER`로 해당 이슈가 사라졌는지 확인하는 절차. 수정이 지적을 없앨지는 재분석 전까지 단정하지 않습니다.

오탐으로 보여도 수정 방법을 제시하고, SonarQube 화면에서 오탐 처리하는 선택지도 함께 적습니다. 오탐 처리가 해결로 인정되는지는 팀 기준을 확인하라고 안내합니다. 같은 규칙의 BLOCKER가 여러 건이면 공통 수정 방법을 한 번 설명하고 위치를 나열할 수 있으며, 수정 방법이 다른 항목은 따로 적습니다.

가이드는 안내만 합니다. 사용자가 수정을 요청하기 전에는 코드를 고치지 않습니다.

## 설정

서버 URL, 토큰, 기본 프로젝트는 `.claude/skills/sonarqube/config.properties`에 있습니다. 스크립트가 실행할 때마다 이 파일을 읽으므로 수정하면 바로 적용됩니다.

```properties
url=<SonarQube 서버 주소>
token=<토큰>
project=<프로젝트 키>
```

처음 사용한다면 `config.example.properties`를 `config.properties`로 복사한 뒤 값을 채웁니다. 토큰은 사용자별로 `<url>/account/security`에서 발급하며, 조회할 프로젝트의 Browse 권한이 필요합니다. `config.properties`는 git에 올라가지 않습니다.

사용자가 URL, 토큰, 프로젝트 변경을 요청하면 해당 줄을 수정합니다. 토큰은 출력하거나 명령줄에 넣거나 답변에 포함하지 않습니다.

## 명령

| 질문 | 명령 |
|---|---|
| 필수 조치가 있는가? | `issues --severities BLOCKER` |
| 어떤 프로젝트가 있는가? | `projects` |
| 프로젝트 상태는 전반적으로 어떤가? | `status` |
| 미해결 이슈는 무엇인가? | `issues [--severities BLOCKER,CRITICAL] [--types BUG,VULNERABILITY,CODE_SMELL] [--path src/main] [--new] [--limit 50]` |
| 해결된 이슈는 무엇인가? | `issues --statuses RESOLVED,CLOSED` |
| 검토할 보안 핫스팟은 무엇인가? | `hotspots [--status TO_REVIEW\|REVIEWED] [--new]` |
| 문제가 많은 파일은 어디인가? | `files --metric code_smells --limit 10` |
| 이 규칙은 무슨 뜻인가? | `rule python:S3516` |
| 시간에 따라 어떻게 변했는가? | `history --metrics bugs,vulnerabilities,code_smells` |
| 이런 API가 있는가? | `catalog issues/search -v`, 전체 목록은 `catalog` |
| 그 외 읽기 전용 호출 | `api qualitygates/get_by_project project=<프로젝트 키>` |

`issues`는 최대 `--limit`건만 나열하지만, 전체 건수와 심각도·유형별 건수는 조건에 맞는 이슈 전체를 기준으로 합니다. 필터로 지정한 속성의 건수 줄은 표시되지 않습니다. 목록의 일부만 보여줄 때는 그 사실을 밝힙니다.

## 결과 해석

- **결과는 마지막 분석 시점 기준입니다.** `projects`의 마지막 분석 일시와 리비전을 `git rev-parse HEAD`와 비교합니다. 다르거나 작업 트리에 변경이 있으면 현재 코드가 반영되지 않았다고 밝힙니다. 수정한 BLOCKER도 재분석 전에는 미해결로 남습니다.
- **품질 게이트 `OK`는 BLOCKER가 없다는 뜻이 아닙니다.** 기본 "Sonar way" 게이트는 새 코드만 검사합니다. 평가된 조건이 0개인 `OK`는 아무것도 측정되지 않았다는 뜻입니다. 조건이 평가된 `OK`도 기존 코드에 대해서는 알려주지 않습니다.
- **핫스팟은 취약점이 아닙니다.** 사람이 검토해야 하는 코드이며 안전한 것으로 판명될 수 있습니다. 보안 리뷰 등급과 보안 등급은 별개입니다.
- **커버리지 0%는 리포트를 가져오지 않았다는 뜻일 수 있습니다.** 테스트가 없다고 말하기 전에 테스트 코드와 커버리지 리포트 설정을 확인합니다.
- **`status`의 분석 경고를 확인합니다.** 결과에 영향을 줄 수 있는 경고는 답변에 적습니다.

## 답변

사용자의 언어로 작성합니다. 이슈 위치는 `경로:줄` 형식으로 쓰고 BLOCKER부터 적습니다. 특정 수치나 규칙을 묻는 질문에는 질문에 답하는 내용만 적습니다.

프로젝트 상태, 문제점, 해결할 항목, 점검 결과를 묻는 질문에는 다음 순서로 답합니다.

1. **판정:** 필수 조치 있음 또는 없음과 BLOCKER 건수. 이어서 품질 게이트 상태와 전체 등급을 참고 정보로 적습니다.
2. **필수 조치 (BLOCKER):** 항목마다 "BLOCKER 수정 가이드"의 내용을 적습니다.
3. **범위:** 분석된 리비전과 일시, 현재 코드와 일치하는지, 대시보드 링크.
4. **등급과 건수:** 신뢰성, 보안, 보안 리뷰, 유지보수성.
5. **권장 사항 (선택):** 취약점, 버그, 위험도 높은 핫스팟 순으로 간단히 적습니다. 코드를 읽어 확인한 항목과 확인하지 않은 항목을 구분합니다.
6. **분석 경고:** 경고 내용과 영향을 받을 수 있는 결과.

스크립트가 HTTP 401 오류를 내면 토큰이 유효하지 않은 것입니다. `<url>/account/security`에서 새로 발급해 `config.properties`의 `token` 줄에 저장합니다. 서버에 연결할 수 없다는 오류가 나면 `url` 값과 네트워크를 확인합니다.
